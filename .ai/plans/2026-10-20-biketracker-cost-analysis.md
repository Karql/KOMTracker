# BikeTracker — Cost analysis (Phase 4, OQ-16)

## Context
Concept §8 / Phase 4: "purchase + services − resale = net cost; cost/km; cost/period", unioning bikes, components, services and expenses. All the data now exists (one real user: 11 bikes ≈ 57k zł, 386 components ≈ 57k zł — 54 used on several bikes, 25 never installed — 216 expenses ≈ 23k zł, services). The maintainer wants a separate, "fancy" tab with charts and tables, drill-down (sources → groups → categories → items), filters (bike, year, include/exclude sources), per-km / per-year summaries and a detailed per-year ledger of a bike's costs (like spritmonitor.de's cost analysis). The cost ledger is only a few hundred lines per user, so it is built once on the server (attribution needs installation windows + mileage) and aggregated in the browser.

## Decisions
- **D-COST-1 Server builds a cost ledger, the browser aggregates.** `GET cost-analysis` returns attributed cost lines + per-bike km (seed and per year); filters, drill-down, charts and tables are pure client-side aggregation (`CostAggregator`, in API.Shared so it is unit-testable). *Why: attribution needs installation windows and activities (server); the result is small, so client-side slicing makes every click instant without an endpoint per view.*
- **D-COST-2 Multi-bike parts are split by distance share** (maintainer). A component's price (and its resale) is divided across bikes by the km it did on each — Tracked windows incl. the in-parent overlap, plus Manual rows on a bike (Manual rows in a parent follow the parent's shares); the initial seed km from before the purchase don't count. Installed but zero km → equal split over those bikes; never installed → "Not on a bike". *Why: per-bike totals add up to the overall total — nothing double-counted — and a wheel ridden mostly on one bike costs mostly that bike.*
- **D-COST-3 Services:** the cost is split equally across the service's targets; a component target goes to the bike it was mounted on **at the service date** (directly or via its parent), else "Not on a bike". *Why: a service is a point in time — the installation history knows exactly which bike benefited, no proportional guesswork needed.*
- **D-COST-4 Cash basis + resale netting** (maintainer). A cost counts on its date (purchase / service / expense); a sale is a negative line on the sale date, split like the purchase. Default view = **net**; a Gross switch shows spending only, with "Recovered from sales" as its own figure. Items without a price (unknown) contribute nothing. *Why: matches how the money actually moved (and spritmonitor); per-year views stay honest and resale stays visible.*
- **D-COST-5 Sources are toggles, all on by default — incl. bike purchases** (maintainer). Bikes · Components · Services · Expenses. Expenses have no bike → "General": counted in the all-bikes view, dropped when a single bike is selected. *Why: the full "what does cycling cost me" picture by default; one click shows running costs without the purchase price that otherwise dominates.*
- **D-COST-6 Per-km = cost ÷ km of the selected bikes in the selected period.** Ride km per bike per year come from Strava activities; a bike's initial seed km count only in "All time". Shown as cost / km and cost / 1000 km, plus per year / per month averages. Per year / month use the years the selection actually covers: an open-ended period starts at the first dated cost or ride in scope and ends this year (or at the last one for a retired bike). *Why: the classic TCO numbers; seed km have no date, so they can't be placed in a year; a bike bought last year must not be averaged over the user's whole history.*
- **D-COST-7 Charts = Blazor-ApexCharts 7.0.0** (maintainer). Donut with click-to-drill-down, stacked bars per year/month, per-bike bars, categories treemap; every card has a chart / table toggle. *Why: animated, interactive and much nicer than MudChart; supports net10 + WASM; a single NuGet.*
  - **Drill-downs are per card** (maintainer feedback): the donut and the year-by-year bars each have their own drill (source → group → category → items; the bars fold the tail beyond 8 series into "Other") and breadcrumbs; a drill re-renders only its own card (`RenderOnChange` keeps the other charts from even receiving new parameters), while a filter change re-renders everything. Each chart also sits in its own `.costs-chart` box (not directly in the card, which stretches to the row's height) and the donut's area keeps its height while the donut is re-created. *Why: Blazor pushes parameters to every chart on any re-render, and ApexCharts redraws / re-animates on any parent resize — a re-created donut briefly changed the row's height and so redrew the treemap next to it; unrelated cards flickered as if they had changed.*
  - **Levels with a single slice are passed through** (`CostAggregator.Drill` / `Up`; breadcrumbs skip them), and bike lines have no type categories (group = category = "Bikes"). *Why: Bikes → "Bikes" (100 %) → "Bikes" was two pointless clicks — there is usually one bike per type — and the same rule fixes Services (one group) and any group holding one category.*
  - **Every entity has its own stable colour** (`CostColors`, built once per report): sources keep their fixed colours; groups, categories and items take slots of an 8-colour categorical palette — siblings never share one, the largest child inherits its parent's slot (Wheels → Wheel), otherwise the least-used slot wins; past 8 slices a view greys the tail. The treemap tiles use the category colours; the treemap ("Biggest categories", single-bike view) leaves the bike purchase out — over all time it took ~85 % of the area and squeezed the parts into slivers, and the donut already shows that split. *(Revised: the first version shaded the drilled source's colour.)* *Why: one-hue shades were dull and hard to tell apart, and didn't match the "Biggest categories" treemap; colour must follow the entity, not its rank in the current view, so "Tire" looks the same in every card and filter.*
  - The stacked bars' Y axis is set explicitly (tallest positive stack ↔ deepest negative one, rounded to 1 / 2 / 2.5 / 5 × 10ⁿ steps). *Why: ApexCharts scales a stacked axis to each bar's net sum, so a year with a resale clipped its positive stack.*
- **D-COST-8 "Parts per 1000 km" follows the filters:** per component category, what components + services cost in the selection ÷ the km ridden in it × 1000 (top 8; empty without km), with how many distinct parts / services make up the amount (a part split over bikes counts once). *(Revised on maintainer feedback: the first version — price ÷ lifetime km of finished wear parts, from the mileage projection — ignored every filter on the page.)* *Why: a card that doesn't react to the period / bike / source filters looked broken next to the ones that do; spend ÷ km in the same scope is consistent with the cost-per-km KPI, needs no extra server data (the report's per-component usage list was dropped) and still answers "what do tyres cost me per 1000 km on this bike / in this year" — on a cash basis, so a year with a big purchase spikes.*
- **D-COST-9 The report types live in Domain and are the wire format** (`CostAnalysisReport`, `CostLine`, `CostBike`). *Why: a read-only report that the server builds and the browser aggregates — both sides need exactly the same shape; a 1:1 view-model copy would add mapping without protecting anything.*
