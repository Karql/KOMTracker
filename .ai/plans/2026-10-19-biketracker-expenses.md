# BikeTracker — Expenses (`bt.expense`, D-20)

## Context
Concept §12 post-v1 item: standalone cost entries that aren't installable parts (clothing, tubes, lube, tools, electronics…). The maintainer keeps ~215 such rows in an Excel sheet (2013–2026, plus a couple of resold items); they must not swamp the components list (D-20). Outcome: an **Expenses** page under Bike Tracker with full CRUD, a detail page, categories, sell/archive lifecycle, filters and place autocomplete. The Excel backlog is imported afterwards by one-off SQL scripts outside the repo. No sums / cost analysis (a separate future feature), no bike link (bike services are a separate future feature), no in-app import/export.

## Decisions
- **D-EXP-1 Own category enum, not ComponentCategory.** `ExpenseCategory` (code-side enum persisted as string, D-13) with single-word names modelled on big bike shops' menus (bike-discount: Parts / Accessories / Clothing / Electronics; r2-bike: Bekleidung, Schläuche & Tubeless, Werkzeug & Wartung, Zubehör): **Clothing, Shoes, Cleats, Helmets, Eyewear · Tubes, Tubeless · Cables, Parts · Tools, Pumps, Lubricants, Cleaning · Electronics, Lights · Bags, Bottles, Locks, Fenders, Accessories · Trainer · Nutrition · Other**, grouped by `ExpenseCategoryGroup` (Clothing, Tyres, Parts, Workshop, Electronics, Accessories, Training, Nutrition, Other) for the picker and later cost rollups. Required, `Other` as the escape hatch. *Why: the 60+ component categories are part types for installation/mileage; only ~6 overlap and clothing/shoes/helmets/lube/electronics are missing — a small purpose-built list gives clean filters and cost buckets. Single names (no "Shoes & cleats" combos) per the maintainer. **Nutrition** (own group) added after the backlog review: drinks/gels/bars are a real cycling cost (shops list "Nutrition" as a top-level menu) and would otherwise land in Other.*
- **D-EXP-2 Lifecycle like components: Active / Archived / Sold** with SaleDate / SalePrice / SalePlace; Sell + Archive actions (dialogs with notes), sale details editable while Sold and kept when leaving Sold. Own `ExpenseLifecycle` enum. *Why: some items get resold (tubeless kit, shoes) or used up; behaving exactly like bikes/components keeps one mental model. Revises D-20's "no lifecycle".*
- **D-EXP-3 No bike link.** *Why: bike services (wheel rebuilds, shock service…) will be their own feature; an expense is bike-agnostic.*
- **D-EXP-4 Fields:** Name (required, 200), Category (required), Price (required, ≥ 0), PurchaseDate (required), PurchasePlace (optional, 200), Notes (optional, 2000) + lifecycle/sale fields; columns `price` / `purchase_date` / `purchase_place`. *Why: every backlog row has a name, date and price (0 exists — a race prize); a required date keeps the year filter meaningful. Named exactly like the bike/component purchase fields (not Amount / Date / Place) so the model is consistent and a bare "Date" is never ambiguous next to SaleDate.*
- **D-EXP-5 Detail page like bikes/components** (`expenses/{id}`): header with category icon, name, category + lifecycle chips and actions (Edit / Sell / Archive / Restore / Delete); panels **Purchase**, **Sale** (when Sold) and **Notes**. List cards/table rows link to it (stretched-link card with a real `href`); the ⋮ menu keeps quick actions. *Why: consistent with bikes/components, where purchase/sale/notes live on the detail page.*
- **D-EXP-6 List features:** search (name / place / category), filters **group**, **category**, **year**, "Show archived / sold" toggle (hidden by default, like components), card/table toggle remembered, newest first, amounts in the preferred currency. **No totals.** *Why: browsing/finding a purchase is this feature's job; totals belong to the dedicated cost-analysis feature.*
- **D-EXP-7 Place autocomplete shared with purchase places:** expense places are merged into `PurchasePlaces` (and expense sale places into `SalePlaces`) of `GET bike-tracker/suggestions`. *Why: the same shops sell parts and expenses; one endpoint keeps every dialog consistent (D-SUG-1).*
- **D-EXP-8 Hand-drawn icons** in the component style (`ExpenseCategoryIcons`), reusing the component SVGs where the item is the same (lights, pump, lock, bottle, fenders, tools, apparel). *Why: visual consistency with the component categories.*
- **D-EXP-9 Backlog import via SQL scripts outside the repo.** *Why: a one-off migration of one user's data; no in-app import/export wanted.*
